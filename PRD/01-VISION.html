01-VISION — 目标/persona/约束假设

PRD-DECISION-IDENTITY DEC-1 产品主叙事:高性能反指纹浏览器运行时(双身份一句式);引擎基座 SpiderMonkey

背景: 项目叙事存在三个来源且不一致:项目 CLAUDE.md 愿景句「高性能反指纹浏览器运行时」(Stealth 为主身份)、.spec/01-BUSINESS 的「统一 Cargo 库全能力对等」、用例清单呈现的完整 Bun 替代工具链。蓝图开放问题1交由 Commander 裁定。

决策: 主叙事采用项目 CLAUDE.md 愿景句序:「高性能反指纹浏览器运行时」为产品主身份;统一运行时的全能力(JS 脚本执行 + Node.js/Bun 生态 API + 无头浏览器)作为能力面并存,以一句式双身份表达。引擎基座选型:SpiderMonkey 替代 JSC,与 servo 共享同一 JS 引擎。叙事顺序用户可改,不影响 17 条 prd-req 集合。
理由: Commander 默认裁定(2026-08-22,可逆,蓝图开放问题1):采用项目 CLAUDE.md 愿景句序,统一运行时全能力表述为能力面而非并列身份。与 servo 共享 SpiderMonkey 引擎使浏览器 DOM 与 Node 互操作发生在同一线程同一引擎,消除双引擎桥接维护成本。

PRD-DECISION-EMBED-SERVO DEC-2 内嵌 servo 浏览器引擎,非外驱 Chrome,无头优先

背景: 反指纹浏览器产品可走两条路:外驱已安装的 Chrome/Chromium(经 DevTools 协议),或把浏览器引擎嵌入自身运行时。

决策: 内嵌 servo 全功能浏览器引擎(DOM/CSS/Layout/渲染),无头(headless)优先,不依赖用户机器上已安装的外部 Chrome。
理由: 单一 Rust 二进制交付——装一个 bao 即得全部能力,符合统一运行时主叙事;反指纹需要引擎层控制权(TLS 指纹、Canvas/WebGL 注入),外驱 Chrome 的能力面受 DevTools 协议限制,做不到网络层指纹接管。

PRD-DECISION-BRAND DEC-3 品牌:用户输入 bao,代码保留 Bun 引用

背景: 项目大量复用 Bun workspace 上游代码,用户可感知命令名与内部代码引用需要一套一致的命名规则。

决策: 用户品牌 bao(CLI 子命令 bao run/bao browser 等);JS 全局对象保留 Bun.* 并提供 Bao.* 别名(同一对象);内部 Rust crate 名 bun_* 不改(保持上游兼容),新建层用 bao_*;环境变量 BUN_* 保留,新增 BAO_* 别名(启动时复制为对应 BUN_*)。原则:用户输入 bao,代码里还是 bun。
理由: 最小化与上游 Bun 的 diff(与 DEC-4 持续合并策略配套);用户交互面统一单一品牌,老 Bun 程序零成本识别既有全局对象。

PRD-DECISION-UPSTREAM DEC-4 持续合并 Bun 上游,最小 diff

背景: Bao 复用 Bun workspace 约 85 个纯 Rust crate 与 servo 上游,长期存在 fork 与上游的漂移张力。

决策: Bun workspace 与 servo 均为上游真源,持续合并上游增量;Bao 层(bao_* crate)只做适配不改上游分层;遇接口冲突改 Bao 层不改上游;上游同步时逐项重放已沉淀的 BAO patch(见项目 CLAUDE.md patch 清单)。
理由: 复用生产验证的高性能实现避免重复建设;最小 diff 策略把每次上游同步的成本与 fork 漂移风险压到最低。

PRD-DECISION-DISTRIBUTION DEC-5 分发形态:Cargo 库 + bao CLI(现目标);npm 非当前目标

背景: .spec/01-BUSINESS 品牌表曾写 npm 包名 bao(npm install -g bao);用户 2026-08-17 crates.io 裁决:不发 CLI 包,cargo 库(170 个)已发布。蓝图开放问题3交由 Commander 裁定。

决策: 分发现目标 = Cargo 库(crates.io)+ 本地构建的 bao CLI 二进制。npm 分发非当前目标,如需须用户书面重启该决策。
理由: 引用用户 2026-08-17 crates.io 裁决(命名与发布工程已完结、170 库已发布,仅余 token/豁免邮件事项);Commander 默认裁定(2026-08-22,可逆,蓝图开放问题3):npm 渠道从产品目标中移除并留书面重启口。

PRD-DEC-UPSTREAM-STRATEGY-V2 上游策略 V2：参考不盲吸 / 兼容超越 bun / 清理构建留痕 / 纯 Rust 优先

背景: bao 对上游 bun/servo 是深度修改的自维护 fork(用户裁决 2026-09-27:完整 fork 自己维护),旧上游策略需升级为 V2。

决策: 上游策略 V2:①BUN 深度修改区不吸收但参考、自己实现;②兼容必须对齐甚至超越 bun 上游(node oracle 为尺);③清理与构建记录留痕;④三方生态支持同等重要、纯 Rust 优先;⑤实现选型阶梯:成熟库 → 翻译同功能他语言库 → 最后才裸写。

①用户原话:「然后我们BUN深度修改了,很多东西可能不吸收但是参考,我们要自己实现」——BUN 深度修改区域的上游变更默认不直接吸收,作为参考自行实现(吸收/自实现按逐项判定)。

②用户原话:「还有就是兼容是必须对齐甚至要超越BUN上游的」——Node.js/Bun 生态兼容以对齐 bun 上游为下限、超越为目标;尺子是 node oracle:上游偏离 node 处保持 node 忠实即为超越。

③用户原话:「清理和构建记录也很重要」——清理工作与构建记录随波执行留痕,不作为可丢弃的附属品。

④用户原话:「3方支持一样重要可以支持,但是我们可以用纯RUST优先」——第三方生态兼容同等重要;技术选型纯 Rust 优先,非 Rust 实现(如 C/C++)仅在无纯 Rust 替代时采用。

⑤用户原话(同日追加裁决):「那我们自己实现也没问题,问题是成熟的库为啥不用呢,如果没有也可以试试看翻译同功能别的语言的库,实在没办法才自己裸写」——自写是最后手段:实现选型先查成熟库(依赖树内/crates.io),无 Rust 库时优先翻译同功能他语言库,两者皆无才裸写。

理由: 用户 2026-09-27 对话四条裁决原话,逐项忠实转录(过渡载体 .plans/spidermonkey-evolution.md 2026-09-27 条目)。

PRD-DECISION-RUNTIME-NAMING DEC-6 公开 API 命名收口:BrowserRuntime / NodeRuntime(2026-09-29 用户裁决)

背景: bao 层有两个公开 BaoRuntime:bao_browser::BaoRuntime(浏览器运行时入口,持有 Servo/PagePool)与 bun_runtime::BaoRuntime(Node.js 运行时入口,持有事件循环/timers)。API 冻结前需收口命名。用户裁决 2026-09-29(AskUserQuestion 直答「收口为 BrowserRuntime/NodeRuntime」)。

决策: 收口为 BrowserRuntime(浏览器运行时入口)与 NodeRuntime(Node.js 运行时入口);旧名 BaoRuntime 保留 deprecated alias 过渡(0.x 允许 breaking,1.0 前收口移除)。三方 crate(bao_browser/bun_runtime/伞 bao)均留 alias。

用户裁决原话:选项「收口为 BrowserRuntime/NodeRuntime」——1.0 前重命名(0.x 允许 breaking),旧名留 deprecated alias 过渡。

实施证据:W2 落地(commit c5260289,94 文件 431 点重命名,三 crate alias;W22a api-surface 三档声明收录 deprecated alias 1.0 过渡清单)。

理由: 同名不同物的心智负担在 1.0 前消除;alias 保证 0.3.x 消费者无感过渡。

PRD-DECISION-CONSOLE-SCOPING DEC-7 console 计时器/计数器混合作用域(2026-09-29 用户裁决)

背景: console.time/timeEnd/count 等的命名空间归属——Bao 同时承载浏览器页面 realm 与 Node CLI realm,两者语义不同(浏览器=per-realm;Node CLI=进程全局)。用户裁决 2026-09-29(AskUserQuestion 直答「混合」)。

决策: 混合作用域:浏览器上下文(页面/iframe/worker/SW)console.time/count 为 per-realm 独立命名空间(浏览器保真);CLI/Node-realm 为进程全局(Node 保真)。双语义在文档明示。

用户裁决原话:选项「混合」——浏览器上下文 per-realm;CLI/Node-realm 进程全局。各场景对齐各自生态,但双语义需文档明确。

实施证据:W3b 落地(commit 23095349)——路由实证:页面 realm 走 servo dom console(GlobalScope per-realm 结构性满足);node_console 进程全局 statics 仅服务 CLI/Node-realm。双向测试锁定:跨 NodeRuntime 共享计数 1/2/3 + 跨页 per-realm 隔离(页 B 从 1 开始,无共享 3)。

理由: 各场景对齐各自生态保真;引擎层无需改动(路由已结构性正确)。
